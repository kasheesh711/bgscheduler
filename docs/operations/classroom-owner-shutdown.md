# Classroom owner restriction and automation shutdown

Any current admin may manually sync Wise (`POST /api/class-assignments/sync-wise`), generate classroom assignments and publish room locations. Force reassign, the legacy `POST /api/admin/sync-wise` route, the session-authenticated fallback of `/api/internal/sync-wise`, and the 5 Data Health classroom job triggers remain restricted to `kevhsh7@gmail.com` only. Existing owner configuration, enabled-account state and session access version are checked on every owner-only operation. Automatic execution is disabled unless `WISE_CLASSROOM_AUTOMATION_ENABLED` is exactly `true` -- while paused, a non-owner admin's sync, run or publish attempt is stopped with the same `AUTOMATION_PAUSED` result Kevin sees (not a silent failure): `run` and the sync-wise guard route return it directly, and the workspace disables the Run and Publish controls outright with a tooltip explaining why.

## Deploy and contain pending work

1. Deploy the restriction through the normal checked release process. Use an isolated worktree when the primary checkout has unrelated changes. The production environment flag must be absent or explicitly `false`; preserve `SUPER_ADMIN_EMAILS` and Kevin's enabled account.
2. Authenticate to each of the five affected internal routes with the cron secret and verify HTTP 200 with `skipped: true`, `paused: true`, and `reason: "AUTOMATION_PAUSED"`. Never print the bearer or environment values. Data Health should show the five jobs as Paused.
3. Run `scripts/stop-nonowner-classroom-publications.ts` using Node 24, `tsx`, the repository tsconfig and a private production env file. It defaults to a read-only inventory. Run with `--apply` to close pending/running jobs whose creator is not Kevin. Save both JSON results privately as the operational record.
4. The transaction preserves counters and publication rows, records the shutdown reason, and invalidates job claim tokens and the matching singleton worker lease. Completed jobs and Kevin's jobs are preserved. An HTTP request already accepted by Wise cannot be recalled; review any interrupted temporary room moves before manually publishing again.
5. Inspect pre-deployment `cron_invocations`, `sync_runs`, publication leases and deployment runtime logs. Wait for earlier functions to terminate (the longest affected route allows 800 seconds); do not mark a still-running sync failed merely to bypass its single-flight guard. Re-run the publication inventory and idempotent `--apply` sweep after old functions have ended. Declare the shutdown complete only after that check.

## Verify permissions

Test owner, ordinary-admin and non-admin sessions against the page and the run, publish and sync-wise-guard routes. An ordinary admin session now succeeds against `run`, `publish` and `POST /api/class-assignments/sync-wise`; a non-admin session still gets 403 (no session gets 401) for all three, and `run` additionally 403s a non-owner's `forceReassign: true`. The legacy `/api/admin/sync-wise`, the internal session fallback and the five Data Health routes remain 403 for any session other than Kevin's -- other users' existing browser tabs must receive 403 when they attempt those specific operations. Unauthenticated action API requests return JSON 401, including requests with no cookie; the page still redirects unauthenticated visitors to login. Use invalid input/nonexistent IDs for owner validation without running a real sync or publishing to Wise.

The page derives `canPublishAndRun` (any admin) and `canForceReassign` (Kevin only) on the server behind Suspense. Run and Publish render for any admin; the force-reassign checkbox is absent for anyone but Kevin. Viewing, refreshing saved data, printing, overrides and manual schedule emails keep their existing access. Tutor room-booking refresh and other Wise integrations are outside the pause.

## Manual publication during the pause

Kevin's authenticated manual publisher still starts a background attempt on request. Any other admin may now also start a publish; while automation is paused, `claimPublishAttempt` still refuses to claim a job whose creator is not Kevin, so a non-owner's job stays pending (deferred) until automation resumes or Kevin retries it -- the workspace additionally disables the **Publish to Wise** button outright for a non-owner admin while paused, so a stuck non-owner job in practice only happens via direct API use bypassing the UI. A retryable Wise failure leaves an owner job pending with its cooldown intact. Automatic recovery remains paused; the dialog enables **Retry publish** after the cooldown, for Kevin. Reopening the page must not leave the retry permanently disabled. A manual retry reuses the pending job and retains the normal single-worker lease and live Wise read-back safeguards.

## Re-enable only on explicit instruction

Set `WISE_CLASSROOM_AUTOMATION_ENABLED=true` and deploy to resume the five schedules together: Wise snapshot sync, next-day classroom preparation, publish recovery, classroom schedule email delivery, and weekend readiness checks/alerts. Review saved plans and remaining pending jobs (Kevin's and any other admin's) first, because eligible pending jobs can resume. Stopped jobs remain failed and cannot silently restart. Force reassign, `/api/admin/sync-wise`, the internal session fallback and the five Data Health job triggers stay exclusive to Kevin even after automation is re-enabled; manual sync/run/publish remain open to any admin.

Do not roll back to code predating the restriction to recover an unrelated issue: that would restore access for other admins and background execution.
