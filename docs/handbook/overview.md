# Handbook — Overview

BGScheduler is the internal admin console that BeGifted Education's non-technical staff use to run their tutoring business on top of [Wise](https://api.wiseapp.live), the third-party scheduling platform that holds the real tutors, sessions, students, and money. Wise is slow and rate-limited, so it is never queried on the request path: scheduled jobs pull it into versioned Postgres snapshots, a fail-closed normalization pipeline resolves identities, modality, and qualifications, and reads are served from a `globalThis`-anchored in-memory index (`src/lib/search/index.ts`). What began as a tutor-availability search has grown into a 22-feature operations platform spanning scheduling, student lifecycle, finance, market intelligence, and data audit — all behind a Google-OAuth session gate with a small public allowlist for machine and token-bearing endpoints (`src/middleware.ts:4-20`).

Features are reached from a six-section tool navigation — Scheduling & Tutors, Student Lifecycle, Finance & Revenue, Market Intelligence, Research & Reference, Data & Audit (`src/lib/navigation/tools.ts:59-90`) — and `/` is a summary hub rather than a redirect (`src/app/(app)/page.tsx:8-19`). Fifteen Vercel Cron entries drive the unattended half of the system (`vercel.json`); see [reference/crons.md](../reference/crons.md).

> **Maturity badges.** No maturity marker exists in code — no `@deprecated`, no status constant, no registry field. Each badge below is the one the feature's own detail page declares and verifies; that page is the canonical home for it. Where a feature doc declines to assert a single badge, this page states the code-verified reach instead.

## Features

### Scheduling & Tutors

**Tutor Search** — *stable*. Answers the question the whole product was built for: which tutors are free for a class at this time, and are they qualified to teach it? An admin picks a day or date, a time window, a class duration, and optional subject/curriculum/level/modality/tutor filters; the engine slices the window into sub-slots and returns a grid of available tutors plus a separate fail-closed "Needs Review" list for anyone whose Wise data could not be resolved safely (`executeSearch`, `src/lib/search/engine.ts:22`, `:128-149`). Nothing on this path touches the database — `executeSearch` runs entirely against the in-memory snapshot index. See [tutor-search](../features/tutor-search.md).

**Tutor Compare** — *no badge asserted; the engine is live, only the standalone route is legacy*. Places 1–3 tutors side by side for one Bangkok week: what each is already teaching, where the same student is double-booked across two of them, and when all of them are simultaneously free (`buildCompareTutor` / `detectConflicts` / `findSharedFreeSlots`, `src/lib/search/compare.ts:225`, `:322`, `:361`). `/compare` is a client-side redirect that preserves `?tutors=` (`src/app/(app)/compare/page.tsx:10-17`) and carries no nav entry; the engine, both API endpoints, and the calendar UI all live inside the search workspace. See [tutor-compare](../features/tutor-compare.md).

**Classroom Assignments** — *stable*. Turns each Bangkok day's Wise sessions into a physical room plan for the centre. A deterministic engine respects capacity, TV needs, online/onsite modality, preferred rooms, and tutor continuity (`assignClassrooms`, `src/lib/classrooms/assignment-engine.ts:293`), produces a reviewable `(session → room)` table with per-row overrides, and — only on an explicit publish action, and only for OFFLINE sessions (`src/lib/classrooms/data.ts:1226`) — writes the room back to Wise as the session `location`. This is the one feature with a routine Wise write path. Two crons wrap it: a 06:45 Bangkok morning automation (`45 23 * * *`) and an admin-email retry ladder (`0,10,20,30 0 * * *`). See [classroom-assignments](../features/classroom-assignments.md).

**LINE Integration** — *stable (Wise write-path dry-run)*. The bridge between BeGifted's LINE Official Account and the rest of the app. It ingests webhook events behind a channel-signature check and a configuration gate that 503s when unset (`src/app/api/line/webhook/route.ts`, `src/lib/line/client.ts`), classifies inbound parent messages, drafts replies plus a deterministic operational plan into a human review queue, resolves the hard "which Wise student is this LINE user?" question through several matchers that may never self-confirm, and runs a schedule bot whose admin allowlist is an env-var id set that disables the bot entirely when unset (`scheduleBotAdminIds`, `src/lib/line/schedule-bot.ts:112`). See [line-integration](../features/line-integration.md).

**Leave Requests** — *committed, cron-scheduled, nav-registered; Wise-facing capability is dry-run only*. Tutor time-off submissions arrive as rows in one Google Sheet tab (`Form Responses 1` on a default spreadsheet id, both env-overridable — `src/lib/leave-requests/config.ts:1-5`). A twice-hourly sync (`15,45 * * * *`) pulls those rows, matches each to a Wise tutor identity in the active snapshot, computes exactly which upcoming sessions overlap the requested window, and emails the admin allowlist about new submissions. Admins then work the queue: set a status, leave a note, write a status string back into the sheet, and generate a preview of the Wise cancellations an operator would still perform by hand. See [leave-requests](../features/leave-requests.md).

**Tutor Profiles** — *stable*. The only place a human writes down what the Wise pipeline does not carry: a parent-safe summary, teaching style, young-learner fit, curriculum experience, and internal use / do-not-use guidance. Profiles are keyed on a tutor's stable `canonicalKey` rather than a snapshot id, so editorial work survives the next 30-minute sync (`src/lib/tutor-business-profiles.ts:230`), and they can be edited one at a time or bulk-imported through a preview/commit pair of endpoints. The AI Scheduler reads them when drafting parent replies. See [tutor-profiles](../features/tutor-profiles.md).

**Room Capacity** — *no single badge fits; partially wired*. Two questions about the centre's rooms. "How hard are they being used?" is fully wired sync → API → dashboard, aggregating Wise sessions onto the room catalogue against a fixed 07:00–21:00 Bangkok open window (`src/lib/room-capacity/utilization.ts:21-24`). "When do we run out?" — the month-pressure and saturation-forecast engines (`analysis.ts`, `forecast.ts`) — is implemented, tested, and authenticated but has no caller outside its own tests, and its sync is registered `manualOnly: true` with no `vercel.json` entry (`src/lib/data-health/cron-registry.ts:343-357`). See [room-capacity](../features/room-capacity.md).

**Post-Class Feedback** — *stable*. For every class Wise says ended, it reads the canonical session detail, preserves each observed teacher-feedback version as immutable evidence, evaluates an objective deadline/content policy, and carries reviewed ฿100 deduction candidates through a finance handoff into a Google-Sheets payout ledger. Four capability roles — viewer, reviewer, finance, access manager — are resolved fresh from Postgres on every request rather than from the JWT (`src/lib/post-class-feedback/access.ts:11-16`). It is read-only toward Wise, writes nothing into Payroll, and starts in `shadow` enforcement mode with a prospective-only activation instant, so sessions ending before activation can never produce a deduction (`schema.ts:3154`). At 32 tables it is the second-largest subsystem in the codebase. See [post-class-feedback](../features/post-class-feedback.md).

**AI Scheduler** — *experimental*. An admin pastes a parent chat; an LLM extracts the scheduling request as strict JSON and the application decides availability with the same `executeSearch` engine manual search uses. The rule is load-bearing and stated in the system prompt itself — *"You never decide availability"* — so the fail-closed guarantees are inherited rather than re-implemented. Prompt and solver behaviour are still moving and are stamped per run (`AI_SCHEDULER_VERSION`, `AI_SCHEDULER_PROMPT_VERSION`, `src/lib/ai/scheduler-service.ts:20-21`), with an offline eval harness re-scoring the feature against fixture and mined-regression cases. See [ai-scheduler](../features/ai-scheduler.md).

**Proposals (Admin Holds)** — *experimental*. Lets an admin temporarily "hold" tutor slots while a deal is still being negotiated, recording who holds what, for which student, on which day and time, and surfacing the hold inside availability search so a second admin does not offer the same slot to a different parent (`proposalHoldBlocksSearchSlot`, `src/lib/proposals/overlap.ts:84`). Holds are advisory overlays local to BGScheduler and are never written to Wise. There is no standalone page or nav entry — the UI is mounted inside the search workspace, and the AI Scheduler is the second consumer. See [proposals](../features/proposals.md).

### Student Lifecycle

**Progress Tests** — *no maturity label asserted; committed, cron-scheduled, nav-registered*. Answers one question for every student-subject pair: have they had eight classes since their last progress test, and what are we doing about it? BeGifted's teaching contract is a progress test every eight attended classes; this feature turns that cadence into a tracked lifecycle — `accumulating → approaching → due → scheduled → completed` (`progressTestStatusEnum`, `src/lib/db/schema.ts:181-189`) — driven off a cross-snapshot attendance ledger that survives the 30-minute Credit Control snapshot rotation. It drives a teacher heads-up email at class 6 of 8, a daily admin digest (`35 0 * * *`), and one-click bilingual parent outreach. Teachers are a first-class sign-in role because of this page (`src/lib/auth-access.ts:75-78`), and its one Wise write capability is off by default (`wiseSessionCreateVerified`, `src/lib/progress-tests/config.ts:49-51`). See [progress-tests](../features/progress-tests.md).

**Student Schedule** — *stable*. Answers one question for one child: what classes does this student have this month? An admin looks a student up by nickname code against the active Credit Control snapshot (`getStudentMonthlySchedule`, `src/lib/student-schedule/data.ts:165`), pages through months, and then either prints the month as a PDF or hands the parent a link. The parent opens that link on their phone with no account and no login, because the capability token in the path *is* the credential: 32 random bytes, only the SHA-256 hash persisted, scoped to exactly one `(studentKey, monthKey)` pair, expiring, and with indistinguishable failure modes so the public page cannot be used as an oracle (`src/lib/student-schedule/links.ts:1-27`). Delivery is either a copied link or the LINE schedule bot, whose grammar is `<code> [YYYY-MM] [send]` behind a `/schedule` trigger (`src/lib/line/schedule-bot-command.ts:21-24`). See [student-schedule](../features/student-schedule.md).

**Learning Plans** — *no badge asserted; committed and nav-registered*. Turns the committed BeGifted General Mathematics syllabus into a printable, student-specific curriculum plan: pick a year group and topics, add the student name plus optional "prepared by" and parent-facing notes, then open a shell-free A4 report that prints from the browser's own dialog. It is deliberately a **stateless document generator** — no student record, no saved plan, nothing synchronized; the entire document state lives in the report URL, with a deliberate notes cap that keeps the query string inside Vercel's request-URI limit (`src/lib/syllabus/report-params.ts:1-9`). The 4,981-skill syllabus is bundled per year into its own server chunk and never reaches the client (`src/lib/syllabus/get-year-syllabus.ts:5-21`). Access is admins plus individually granted teachers, resolved fresh from a dedicated grant table on every request and failing closed on any database error (`resolveLearningPlansAccess`, `src/lib/learning-plans/access.ts:72-114`). See [learning-plans](../features/learning-plans.md).

**Student Promotions** — *stable*. The academic-year rollover for the Wise tenant: on July 1, 2026 (Asia/Bangkok) every accepted student's `Current Year/Grade level` registration answer moves up one year, classes on a year-band course subject move to the next band, Year 13 students are graduated by explicit human decision rather than incremented, and the pay-rate consequences are reviewed before anything is written back to Wise. The code enforces an audit → review → verify → apply → readback pipeline: every intended write is persisted as a typed row first, revalidated against live Wise immediately before it fires, and its response or error stored back on the row. Both the target date and the run lookup are hard-coded (`STUDENT_PROMOTION_TARGET_DATE`, `src/lib/student-promotions/rules.ts:1`), and the single annual cron refuses to run on any other Bangkok date (`src/app/api/internal/student-promotions/july-1/route.ts:27-31`). See [student-promotions](../features/student-promotions.md).

**University Admissions** — *no badge asserted; merged to `main`, nav-registered, cron-scheduled*. The counselor case-management workspace at `/admissions` that replaces BeGifted's per-student "SummitEd" Google Sheets workbooks: checklist, college list with an append-only decision chain, applications, essays, activities, testing, meetings, notes, announcements, resources, and a deadline calendar. Four roles share it — admin, counselor (assigned cases only), student (self-report sections), and parent (view-only, Thai-first, built strictly by a whitelisted projection helper, `src/lib/admissions/parent-projection.ts`) — with every API request re-checking case membership in Postgres (`requireCaseAccess`, `src/lib/admissions/access.ts:117`). At 36 `admissions_*` tables it is the largest subsystem in the codebase; a daily `12 1 * * *` cron drives its notification pipeline. See [university-admissions](../features/university-admissions.md).

### Finance & Revenue

**Sales Dashboard** — *stable*. Imports the sales team's monthly Google Sheets into a governed Postgres dataset and renders the GM readout on top: revenue pace against target, the trial → new-student → renewal pipeline, and actuals against an imported Bear/Base/Bull scenario projection. It is read-only toward Google on this path, refreshes twice an hour (`sync-sales-dashboard`, `10,40 * * * *`), and owns the shared Sheets access layer (`src/lib/sales-dashboard/sheets.ts`) that other features borrow. See [sales-dashboard](../features/sales-dashboard.md).

**Credit Control** — *live*. Keeps students' prepaid class credits from running out unnoticed. A twice-hourly sync (`20,50 * * * *`) pulls students, packages, past sessions, and future bookings from Wise, projects each package forward to the point it crosses the alert threshold and the point it hits zero, and ranks the at-risk into a per-admin follow-up queue with `contacted` / `pending-callback` / `resolved` outreach state and a zero-balance auto-churn rule (`computePriorityScore`, `src/lib/credit-control/analytics.ts:135`; `computeChurnTransitions`, `churn.ts:85`). Nothing is written back to Wise; the only owned state is human state. Its snapshot tables have quietly become the institute-wide student/session store that Student Schedule, Progress Tests, and Student Promotions all read from. See [credit-control](../features/credit-control.md).

**Payroll** — *stable*. Reconciles what BeGifted paid its tutors against what Wise says happened, one Asia/Bangkok calendar month at a time (`assertPayrollMonth`, `src/lib/payroll/domain.ts:79`). It joins ended sessions and payout invoices to the active identity snapshot and each teacher's tier tag, prices invoices against a versioned rate card (`parsePayRateRows`, `src/lib/payroll/rate-card.ts:98`), aggregates hours and amounts per tutor, and emits typed integrity issues for a reviewer to adjust and approve. The review gate is `auth()` only — there is no role model behind "approval". See [payroll](../features/payroll.md).

### Market Intelligence & Research

**Competitor Intelligence** — *stable*. A market-watching workbench at `/competitor-intelligence` that answers what the other Bangkok tutoring and admissions companies just did, and whether BeGifted needs to respond. A weekly pipeline (`sync-competitor-intelligence`, `25 18 * * 0` — Monday 01:25 Bangkok, the only weekly cron in the file) pulls competitor website copy, Instagram/Facebook posts via Apify, and Google SERP rankings via DataForSEO across a seed of eleven competitor entities plus BeGifted itself (`src/lib/competitor-intelligence/default-sources.ts`), turns each signal into a scored evidence item, and builds a daily brief plus a 90-day War Room attention matrix (`WAR_ROOM_LOOKBACK_DAYS = 90`, `src/lib/competitor-intelligence/war-room.ts:21`). Suggestions are never auto-executed — a human accepts one, which promotes it into a tracked task with an owner and a status. See [competitor-intelligence](../features/competitor-intelligence.md).

**US Universities (IPEDS)** — *stable*. A read-only research console over a curated slice of the federal IPEDS release — the institutions that clear an active / Title IV / four-year / degree-granting gate (`isFourYearDegreeGranting`, `src/lib/us-universities/constants.ts:143-154`) — with their admissions funnel, test-score bands, cost ladder, outcomes, demographics, and conferred-degree mix, plus a five-year admissions trend. It is not a live integration: IPEDS ships as a multi-hundred-megabyte Access database, so the whole ingest is an offline, operator-run pipeline and the running app only ever reads Postgres. Unreported values become `null`, never `0` (`coerceIpedsNumber`, `src/lib/us-universities/parser.ts:6-17`), and every read surface renders an em dash rather than imply a real zero. It feeds the Admissions college list, which soft-references `ipeds_institutions.unitId` without an FK. See [us-universities](../features/us-universities.md).

### Data & Audit

**Wise Activity Audit** — *stable*. A read-only mirror of what happened *inside* Wise: a filterable, paginated timeline of session, billing, invoice, user, and classroom events with the original payload retained for forensics, refreshed every half hour (`sync-wise-activity`, `5,35 * * * *`; `syncWiseActivityEvents`, `src/lib/wise-activity/sync.ts:152`). On top of it sits a package-sales reconciliation workbench that scores Wise receipt transactions as candidate evidence for each Sales-Dashboard row and reports the sheet-vs-Wise revenue variance (`buildPackageSalesReconciliation`, `reconciliation.ts:618`). See [wise-activity-audit](../features/wise-activity-audit.md).

**Data Health** — *wired end to end at HEAD*. The operations command centre, and the page to open first when something looks wrong. It answers three questions: did the scheduled jobs actually fire (every cron evaluated against a typed registry plus invocation-audit rows — `getCronJobsHealth`, `src/lib/data-health/dashboard.ts:878`), is each domain's data fresh enough to trust, and what did normalization refuse to resolve (unresolved aliases, modality issues, unmapped tags from the active snapshot). Its own watchdog cron runs at `7,37 * * * *`. Whether those crons actually fire in production is a runtime fact this repository cannot attest. See [data-health](../features/data-health.md).

## System scale

At this revision the application comprises **188 database tables** (`pgTable` declarations in `src/lib/db/schema.ts`), **241 HTTP endpoints** (method exports across 178 `src/app/api/**/route.ts` files, counting the two destructured from the Auth.js catch-all handler), and **25 admin pages** (`page.tsx` files under the `src/app/(app)/` route group) — plus the login page, the token-gated public parent schedule page, and two shell-free `(print)` reports. The two largest subsystems by table count are University Admissions (36) and Post-Class Feedback (32); Competitor Intelligence holds 16, Progress Tests 8, and US Universities 3. For the mechanical inventory behind those numbers see the [API reference index](../reference/api/index.md) and the [database reference index](../reference/database/index.md).
