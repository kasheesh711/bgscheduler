# Quick Task 260730-j0c — Finalize targets the oldest un-finalized payout run

## Problem

`runPayoutFinalizePass` (src/lib/post-class-feedback/payout-accrual.ts) resolves its
target as `payoutRunWindow(payoutBangkokDate(now).slice(0, 7))`. That anchors the pass
to `now`'s own Bangkok calendar month, so for anchor month M it can only act between
M-26 and the last day of M. On the 1st of M+1 the anchor rolls forward to a window that
has not ended, the pass returns `{ skipped: "window-not-ended" }`, and the M window is
never finalized automatically again.

Consequences when finalize fails for that 5-6 day stretch:
- the period silently reverts to needing a manual operator publish;
- the roll CLI's strict-close preflight (`inspectPayoutRunCloseReadiness` →
  `not_published`) stays blocked, so the next period's accrued deduction rows land in a
  workbook still pointed at the old window.

Fail-safe but invisible, and it defeats the "no human clicks" goal exactly when
something has already gone wrong.

## Approach

**Selector, not calendar arithmetic.** Finalize asks the database which window still
owes a finalize, ordered oldest first, and only falls back to deriving a window from the
clock when no run row exists at all (the day-26 first-publish path, which must keep
working — publish creates the run row on demand).

Resolution order in `runPayoutFinalizePass`:

1. `findOldestUnfinalizedPayoutRun(db, today)` — earliest `post_class_payout_runs` row
   with `window_end < today` (Bangkok) and `status NOT IN ('published', 'closed')`.
   This is the fix: a stranded window keeps being targeted for as long as it exists.
2. Otherwise the calendar-derived window for `today`'s own month, kept behind the
   existing `today <= windowEnd → skip` guard. Unchanged behaviour, and it is the only
   path that can mint a brand-new run, so the pass never publishes an empty run for a
   window the system never observed.
3. Otherwise `{ skipped: "window-not-ended" }`.

Both branches only ever hand `publishPayoutRun` a window that has already ended, so the
operator-mode window guard still holds and the pass stays idempotent: `published` and
`closed` runs are excluded by the selector, and every conflict (lease held, source sync
active, stale token/version) is caught and returned as `{ skipped }` for the next tick.

**Alert.** A window left un-finalized past its month end is surfaced through the
existing cron watchdog rather than a new mechanism. A pure classifier decides staleness
(anchor month strictly older than the current Bangkok month, run absent or not
published/closed); the watchdog maps a stale result onto a synthetic `CronJobHealth`
entry and appends it to the swept jobs, reusing episode dedup, the digest email, and the
recovery notice verbatim. The check is gated on the accrual cron actually being
scheduled, so while the route ships parked (`schedule: null`) it stays inert and cannot
alert on production's current write-disabled state. Any failure inside the check is
caught and logged — the watchdog is a live cron and must not regress.
