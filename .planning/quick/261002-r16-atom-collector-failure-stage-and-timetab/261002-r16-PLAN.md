# Atom collection incident 2 Oct 17:37 BKK: diagnosis and fix

## Context

The autowriter raised a critical `scan_failed` incident: "Atom collection needs attention: collection_failed". The alert email also failed. I checked prod with read-only queries, which the user approved.

**What happened (confirmed from prod rows):**
- Run `6c68a47f`, started 10:36:40Z (17:36 BKK), failed after 21 s with `catalog_n = 0` and **no `feedback_atom_timetables` rows**. So it failed in the Wise timetable read (`fetchDays`), before the Atom browser opened.
- This was the first run of the day with a pending lesson: `6a8abf58ee79651b10af02e8`, which ended at 10:30Z (17:30 BKK). Earlier runs had empty `dates`, so they made no Wise read. Every run since 10:51Z has succeeded and written timetables. **The failure was transient and has already cleared. No feedback was lost** (the lesson-only path continued, and that session later went to `skipped_scope`).
- Most likely mechanism: a race at the class boundary. For a "today" date, `fetchAtomLessonTimetable` (`src/lib/feedback-autowriter/atom/wise.ts`) merges the PAST day read with the full FUTURE listing. Six minutes after classes end, the same occurrence can still be in both listings, but with different `meetingStatus`. `ownership()` hashes `status`, so it throws `"Wise timetable occurrences conflict"`. Strict pagination drift in `fetchAllInstituteSessions` / `fetchWiseSessionsForBangkokDates` is the other candidate, because sessions move between listings while pages are read. Both are plain `Error`s, so `runAtomCollector` reduces them to `collection_failed`.
- **The root problem is observability.** `AtomCollectionError.stage` and the cause of any non-Atom error are discarded. The run row and incident store only `{runId, code}`, so the exact mechanism cannot be proven after the fact.
- Separate finding: run `4b069668` (08:21Z) hung and was marked `abandoned`. Its `cron_invocations` row is stuck at `running`. Note it only; it is out of scope.

**Alert email failure:** the Apps Script MailApp relay is out of quota. `classroom_admin_email_recipients` and `classroom_schedule_email_recipients` show "MailApp daily recipient quota is exhausted" today. The autowriter shares the same `primary` relay. No LINE target is configured (`pushed_channels` is email only). The incident retries hourly, up to 5 attempts.

## Fix (one PR, draft until review)

Work in `.claude/worktrees/slot-a` (its branch `feat/autowriter-luna-rollout` is merged). Branch `fix/atom-timetable-transition` from `origin/main`, run through `/gsd-quick`. Codex has an open worktree `codex/atom-cloud-activation`, so keep the diff to the files below.

1. **Record the failing stage (no secrets, no message text)**, in `src/lib/feedback-autowriter/atom/collector.ts`:
   - Track a `stage` variable through `runAtomCollector`: `pending_query` → `wise_timetable` → `timetable_write` → `link_lookup` → `atom_open` → `atom_collect`.
   - On failure, store `stage`, `AtomCollectionError.stage` (when present), and a fixed `cause` label. For Wise errors, map known messages to slugs: `timetable_conflict`, `pagination_incomplete`, `time_budget`, otherwise `error.name`. Never store the raw message.
   - Write these into `RUN.counts` (`failureStage`, `failureCause`) and into the incident `detail`. Append the stage to the incident summary, e.g. `collection_failed (wise_timetable: timetable_conflict)`. Keep `dedupeKey` unchanged.
2. **Tolerate the expected ended-class transition** in `src/lib/feedback-autowriter/atom/wise.ts`:
   - Remove `status` from `ownership()`. Keep teacher, students, start/end, title, type, classId and programme strict.
   - Add a separate check: if the statuses differ and either side is `CANCELLED`/`CANCELED`, still throw (fail closed, since `lessonsFromWise` drops cancelled sessions). Otherwise keep the PAST record.
3. **Tests**, in `src/lib/feedback-autowriter/__tests__/atom-wise.test.ts`:
   - Change the `meetingStatus` case in the `it.each` to expect coalescing for STARTED/SCHEDULED vs ENDED (PAST wins).
   - Add a case where CANCELLED vs ENDED still rejects. Keep the students/userId/start conflict cases.
   - In the collector unit/integration test (`atom.integration.test.ts` or a unit test around `runAtomCollector` with a throwing `fetchDays`), assert that `counts.failureStage = "wise_timetable"`, the incident `detail.stage` is set, and no raw message is stored.
4. Docs: one line in `docs/operations/iseb-atom-feedback.md` under "Failure and rollback" covering the new stage/cause fields and the transition rule.

Reuse the existing `AtomCollectionError` (`atom/normalize.ts`), `recordIncident` (`incidents.ts`) and `bangkokDate`. No migration: `counts` and `detail` are already jsonb.
