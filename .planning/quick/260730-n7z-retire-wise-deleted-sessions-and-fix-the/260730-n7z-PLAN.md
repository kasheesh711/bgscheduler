# Unblock post-class-feedback activation

## Context

The post-class-feedback system has been stuck in shadow mode since **25 July 2026** and cannot be
activated. Two independent defects block it, and fixing either alone leaves it blocked.

**Defect 1 — deleted Wise sessions are retried forever.** When a session is deleted in Wise, its
detail fetch returns HTTP 400 "Session not found!". The collector records a `session_not_found`
source issue and retries the session on the next run, indefinitely. Verified in production:

| | |
|---|---|
| Open `session_not_found` issues | 230 (plus 35 open `detail_retry` `contract_error` rows on the same sessions) |
| Distinct deleted sessions in the retry pool | 121 |
| Sessions retried in the last 24h | 33 — **all 33 have a `SessionDeletedEvent`** |
| Wise calls burned per run on dead sessions | ~21–30 of a 50-call budget |

The retry engine is **lane 0**, `listFeedbackEventCandidates` ([repository.ts:739-792](src/lib/post-class-feedback/repository.ts:739)),
which selects unlinked `SessionFeedbackSubmittedEvent` rows. A link row is only written by
`saveObservation`, which requires a successful detail fetch — so a deleted session can never become
linked and never leaves the lane. It is `PRIORITY.feedback_event = 0`, the highest lane, and it has
**no grace window**. The existing REC-02 grace (`MISSING_SESSION_RETRY_GRACE_MS`, 7 days,
[repository.ts:29-35](src/lib/post-class-feedback/repository.ts:29)) covers only recheck lane 3, so
it does not stop this. *(An earlier read of this attributed the loop to lanes 1/3 and predicted the
backlog would self-clear around 2 Aug. That was wrong — verified: all 33 retried sessions sit in the
lane-0 pool, which re-supplies them every run forever.)*

The system already stores the deletion fact — `wise_activity_events` holds 11,405
`SessionDeletedEvent` rows with a pre-extracted, indexed `session_id`. **Nothing in
`src/lib/post-class-feedback/` reads it.**

**Defect 2 — the activation gate measures the wrong thing.**
[sync.ts:916](src/lib/post-class-feedback/sync.ts:916) sets `outcome = sourceIssueCount > 0 ?
"partial" : "success"`, and `sourceIssueCount` increments for purely session-scoped facts —
`identity_ambiguous` ([sync.ts:888](src/lib/post-class-feedback/sync.ts:888)),
`billing_evidence_missing` ([sync.ts:901](src/lib/post-class-feedback/sync.ts:901)). The shadow gate
requires `outcome === "success"` ([shadow-review.ts:30](src/lib/post-class-feedback/shadow-review.ts:30)),
so **one messy session out of fifty blocks activation**. Nine `billing_evidence_missing` issues are
open right now, so retiring the deleted sessions alone buys only weeks.

This conflation is unique to the shadow gate. Every other money-adjacent gate filters to
`scope = 'global'` — `payout-plan.ts:88`, `actions.ts:371`, `notifications.ts:339`,
`payout-repository.ts:241`. The run already computes the right signal two lines below at
[sync.ts:944-945](src/lib/post-class-feedback/sync.ts:944): `globalSourceHealthy` (read only by
REC-01) and `mappingObservedHealthy` (**written and read nowhere — dead metadata**).

Blocking on a session-scoped issue buys zero safety: [policy.ts:534](src/lib/post-class-feedback/policy.ts:534)
already returns `assessed: false, deductionCandidate: false` for any session whose `sourceStatus !==
"ready"`. Such a session is structurally incapable of producing a ฿100 deduction.

**Outcome:** a clean shadow sync, an unblocked review button, and a gate that measures pipeline
health rather than data tidiness — with an audited human acknowledgement where judgement is needed.

## Decisions taken

- **Both defects in scope.**
- **Audited acknowledgement**, modelled on `assertPayoutRunPublishable`
  ([payout-plan.ts:84-131](src/lib/post-class-feedback/payout-plan.ts:84)): pipeline-health
  conditions stay absolute and automatic; the session-issue *rate* is overridable only by echoing
  the exact server-computed count plus a reason, recorded in `post_class_config_audit_log`.
- **Do not** retire sessions on absence of a `SessionDeletedEvent`. 108 issues predate the event
  mirror's floor (2026-05-27); absence is not proof. They get the grace window instead.

## Implementation

### Step 1 — migration 0062

Add to `postClassSessions` in [schema.ts](src/lib/db/schema.ts) (~:3237-3282):

```ts
wiseDeletedAt: timestamp("wise_deleted_at", { withTimezone: true }),
```
plus a partial index `pc_sessions_wise_deleted_idx ON (wise_deleted_at) WHERE NOT NULL`.

Mirrors the 0058 `source_status_before` precedent — the deletion is a *fact*, orthogonal to
`source_status` and `eligible`, so no existing reader changes meaning. `npm run db:generate`, rename
to `drizzle/0062_post_class_deleted_sessions.sql`, update `drizzle/meta/_journal.json` (`idx: 62`).
**Trim the generated SQL** — `db:generate` emits catch-up noise on this repo.

Rejected: a new `source_status` enum value. It reaches only the 8 row-bearing sessions, and every
`<> 'ready'` reader treats it as blocking, so retired sessions would sit in the coverage denominator
forever — perpetuating the drag it was meant to remove.

### Step 2 — filter deleted sessions out of the candidate lanes *(the fix)*

In [repository.ts](src/lib/post-class-feedback/repository.ts). Add a module-level SQL fragment:

```sql
NOT EXISTS (SELECT 1 FROM wise_activity_events d
            WHERE d.event_name = 'SessionDeletedEvent' AND d.session_id = <expr>)
```

- **Lane 0** `listFeedbackEventCandidates` (:766-770) — add to the `and(...)`. **Must be inside the
  SQL, before `LIMIT`**: a post-hoc filter would drop the candidates but not let the paging loop
  reach the live sessions behind them, so the run would simply do fewer fetches.
- **Lane 1** (:798-812) — add the anti-join plus `isNull(wiseDeletedAt)`.
- **Lane 3** (:826-846) — filter in TypeScript after `postClassRetryCandidateFromIssueDetails`
  against one pre-loaded set of deleted ids.
- Extract the REC-02 grace predicate (:838-845) into a shared helper and apply it to **lanes 0 and 1
  as well as 3**, so the 108 evidence-free sessions also stop being retried after 7 days.
- `filterCandidatesForFetch` (:1053-1080) — select `wiseDeletedAt` and drop those candidates.

Performance verified against production with `EXPLAIN (ANALYZE, BUFFERS)`: **64.8 ms with the
anti-join vs 89.2 ms baseline**. It plans as a Nested Loop Anti Join on the existing
`wise_activity_events_session_idx`. **No new composite index** — it would save ~1 ms on a 126 MB
table while taxing the busiest ingest path.

### Step 3 — retirement sweep

Add **optional** `retireDeletedWiseSessions?(runId, observedAt)` to the `PostClassFeedbackRepository`
interface (:122-178) — optional is mandatory, since ~10 hand-rolled fakes in `sync.test.ts`
implement it as complete object literals and a required method breaks all of them.

Wrap in `withPostClassTransaction` + `lockPostClassFinance(tx)` +
`assertPostClassSyncSourceWriteFence(tx, runId)` — it writes the same source-truth surface as
`recordSourceIssue`, so it must respect the payout lease. Two statements:

1. Resolve open session-scoped issues with deletion evidence. Session id resolves via
   `coalesce(details->'retryCandidate'->>'sessionId', (select wise_session_id from
   post_class_sessions where id = i.session_id))` — **228 of 230 are orphans with a null
   `session_id`**, so the existing `resolvedPostClassSessionIssueUpdate` (:518-535) does **not**
   apply; it requires the internal UUID. Add a sibling `retiredPostClassSourceIssueUpdate`. Use
   `status = 'resolved'` (not a new value — every consumer filters on `'open'`, and a new value
   would bypass the fingerprint-archival branch at :1720-1730 and silently flip back to open).
   Distinguish via `details.retiredReason = 'wise_session_deleted'`. Sweep measured at **1.46 ms,
   retires 157 issues** (122 `session_not_found` + 35 `detail_retry`).
2. Update matching sessions: `wiseDeletedAt`, `eligible = false`,
   `eligibilityReason = 'deleted_in_wise'`. Add that reason to `SESSION_ELIGIBILITY_REASONS`
   ([types.ts:183-193](src/lib/post-class-feedback/types.ts:183)) and a label to
   `ELIGIBILITY_REASON_LABELS` (`feedback-ui.tsx:122-133`), else it renders "Unknown eligibility
   reason". **Do not** add it to `KNOWN_INELIGIBLE_REASON_VALUES` (:367-374) — that feeds the
   one-terminal-row-per-run readmission lane, and a deleted session must never be readmitted.

Call it in `syncPostClassFeedback` right after `beginSync` (~:588-594) and **before** the candidate
`Promise.all` (~:597-621). Report counts in `completeSync` metadata as `retiredDeletedSessions`;
**do not** add them to `sourceIssueCount`. No backfill script needed — the 157 drain on the first
run after deploy.

**Ship Steps 2 and 3 in one commit.** Step 3 without Step 2 resolves issues that the next run
immediately re-opens under archived fingerprints.

### Step 4 — outcome semantics

[sync.ts:916](src/lib/post-class-feedback/sync.ts:916) — narrow to run-level source health:

```ts
const status = blockingGlobalSourceIssue || firstFormDrift || widespreadContractBreach
  ? "partial" : "success";
```

Keep `sourceIssueCount` as the honest per-session tally on the run row and in Data Health.

Also add a `readySessionCount` in the observation loop (~:844-848) where `sourceStatus` is derived,
and write it to metadata. Do **not** threshold on `sourceIssueCount` — it double-counts (:690 and
:697 both fire for one failed fetch) and mixes in global escalations.

### Step 5 — the gate

Replace `selectFreshPostClassShadowSync` ([shadow-review.ts:15-37](src/lib/post-class-feedback/shadow-review.ts:15))
— one caller, one test file, clean to swap — with a pure classifier returning a structured verdict,
following the `classifyPayoutWindowStaleness` precedent shipped earlier today:

```ts
classifyPostClassShadowReviewEvidence(runs, {
  policyVersion, mappingVersion, mappingUpdatedAt, openBlockingGlobalIssues, acknowledgements,
}) -> { evidence, conditions: [{ key, passed, detail }], blockedBy, acknowledgeable, ready }
```

Conditions, keeping every existing one except `outcome`:

- **Absolute:** `globalSourceHealthy === true`; `mappingObservedHealthy === true` (promotes dead
  metadata to the gate's primary mapping proof — this is the field that actually proves the current
  mapping parsed a real Wise payload); **zero open blocking `scope = 'global'` issues, queried live**
  (new — the current gate reads a historical per-run counter, unlike every other money gate);
  freshness vs mapping edit; version match; non-emptiness. Missing metadata keys fail closed.
- **Acknowledgeable:** readability `detailFetchedCount / candidateCount` and resolvability
  `readySessionCount / sessionCount`, both ≥ 80%. Threshold is a judgement call, deliberately
  acknowledgeable so a wrong number costs a dialog, not a shipped feature.

Extract `openBlockingGlobalSourceIssueCount(db)` as one shared helper — the predicate is currently
duplicated in four places.

Route ([shadow-review/route.ts](src/app/api/post-class-feedback/shadow-review/route.ts)): extend
`BodySchema` with `acknowledgeSessionIssues?: number` (must equal the server-computed count — a
stale tab must not wave through a number that has grown) and `reason?: string`, required when
acknowledging. Build the 400 from `blockedBy` so it names the failing condition instead of today's
undifferentiated eight-condition sentence. Extend the audit `afterValue` in
`markPostClassShadowReviewed` ([settings.ts:355-392](src/lib/post-class-feedback/settings.ts:355))
with the acknowledged count, reason, and condition snapshot.

- Return open-issue counts in the settings payload — `openIssues` is already loaded at

- **Third consumer:** [data-health/dashboard.ts:386-391](src/lib/data-health/dashboard.ts:386)
  `postClassFeedbackOutcome` also reads `metadata.outcome`, and :512-513 computes `lastSuccessAt`

- `settings-tab.tsx` — render blockers persistently; add the acknowledgement dialog. Preserve the

- **Use one shared query helper for the candidate run set.** dashboard.ts:163 loads 8 runs of any
  status; the route loads 20 with `status = "success"`. Divergent inputs would make the checklist

### Step 7 — payout belt-and-braces

## Risks

- **Lane 0 currently masks work.** Once ~121 deleted sessions stop occupying it, the collector will
  start fetching the 108 pre-mirror sessions and may surface a burst of new `session_not_found`
  issues. With Step 4 in place these block nothing, but the Data Health count spikes before it falls.
  **Deploy Steps 2–5 together** — Step 2 without Step 4 makes the symptom look worse first.
- **108 evidence-free issues are inference, not proof.** All predate the `SessionDeletedEvent` floor
  and none ever obtained a session row, but that is circumstantial. One `GET` against Wise for a
  single id would settle it — worth doing before Step 5 ships.
- **One session sits inside the live payout window.** `6a25254705d397959631f664` (ends 2026-07-27) is
  currently `eligible = true, source_status = 'ready'` and is deleted in Wise. Retiring it is correct
  and conservative, but it moves a live window's denominator by one — flag to finance before deploy.
- **Historical numbers move.** `6a584f90055db8535fb7d97c` carries 17 assessments; setting
  `eligible = false` shifts the compliance denominator by one with no obvious cause unless noted.
- **Legacy runs fail closed** on the new metadata keys — correct, but the gate is unusable until one
  fresh shadow sync completes after deploy. Put this in the runbook.
- **`policyVersion` is never incremented anywhere** (declared default 1, only ever read), so that
  gate condition is inert. Harmless today; the latent bug is that a future policy change would
  silently reuse old assessments. Out of scope — worth its own ticket.
- **Out of scope, but noticed:** 1,934 of 2,281 July sessions are `source_status <> 'ready'` (84%),
  only 3 of them deleted. `assertPayoutRunPublishable`'s unreconciled-ratio gate is therefore firing
  on something unrelated to this work. Worth investigating separately before the first payout run.
