# Quick Task 260807-d12 — Summary

## What was built

An in-app off switch. `MAINTENANCE_MODE=true` blocks the staff UI while all 15
Vercel Crons keep running, so there is no data gap to backfill on resume.

Vercel's Pause Project was the obvious first answer and is wrong for this: it
blocks the production deployment, and the crons target that same deployment, so
pausing stops the syncs too. The gate therefore lives in `src/middleware.ts`,
above the auth check.

## Design decisions worth keeping

**Fail-open polarity (MAINT-01).** The flag engages only on the exact string
`"true"`. Unset, empty, `"TRUE"`, `"1"`, or a typo all leave the site serving.
This is deliberately the inverse of `ENABLE_STUDENT_SCHEDULE_LIVE`'s `!== "false"`
— that flag defaults on and opts out, this one defaults off and opts in, because
a bad env value must never black out production. The bypass allowlist runs the
other way and is fail-closed, mirroring `scheduleBotAdminIds`.

**Gate ordering is load-bearing (MAINT-04).** The check sits above
`isPublicRoute`, not below it. `isPublicRoute` allowlists `/api/line/webhook`, so
a gate placed after it would wave through the one path the switch is meant to
close.

**No `@/lib/env` import.** `src/lib/maintenance.ts` reads `process.env` directly.
`src/lib/env.ts` calls `getEnv()` at module load and throws on a partial
environment, and middleware runs on the edge. The Zod declarations added there
are inventory parity only.

## Known cost, accepted by the user

`/api/line/webhook` is **not** exempt. LINE does not redeliver webhooks by
default, so inbound OA messages arriving during a maintenance window are **lost,
not queued** — no thread, no contact row, no scheduler review. The user was shown
this trade-off explicitly and chose it. Two follow-ups are documented in runbook
§4.2: read the LINE OA app manually for the window, and check the LINE Developers
console afterwards in case a run of failed deliveries left the endpoint flagged.

Reversing this is a one-line addition to `MAINTENANCE_EXEMPT_PREFIXES`.

The `401` on the cron path is the proof that matters: the body is
`{"error":"Unauthorized"}` from `src/lib/internal/cron-auth.ts`, **not** the
gate's `{"error":"Service unavailable — maintenance mode"}`. The gate passed the
request through to its handler, which then rejected an unauthenticated curl.
Response shapes confirmed: JSON + `retry-after: 3600` under `/api/`, HTML
elsewhere.
